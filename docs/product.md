# Analyst console scope

The local console is a governed analyst-review surface, not an automated decisioning product. Its v1 endpoint exposes exact supported payment trends plus country, channel, and customer-segment breakdowns. Its v2 endpoint is a two-step Azure Foundry proposal contract: a reviewed SQL proposal is created without execution, then a short-lived explicit approval token is required and SQL plus snapshot state are revalidated before read-only execution. Pending proposals are SQLite-backed, single-use, and expire after five minutes; they contain review metadata and SQL but no analyst question or result rows. Each result includes generated SQL, validation steps, preview, trace/latency/cost, snapshot state, and generated evaluation evidence.

Language-model context is restricted to the curated semantic catalog. Identifier-like source fields are not included in that catalog, returned result preview, or lifecycle event payloads; physical join keys remain implementation mechanics only. Raw analyst questions and result rows are not written to structured lifecycle logs.

The permitted source is synthetic mobile-money data. It is domain inspiration only and must not be represented as bank, cardholder, or customer data. The approved V2 contract exposes simulation step, transaction type, amount, balance features, and source-provided fraud label. Simulation step, transaction type, amount, and fraud label are required; the four balance features are nullable and preserve source nulls. It excludes `initiator` and `recipient` and does not manufacture a calendar timestamp. Any model-risk use requires separate feature definitions, model validation, human approval, monitoring, incident response, and rollback. This repository does not train, score, or make fraud decisions.

## Enforced limits and remaining limitations

The local query connection is read-only and capped at 512MB, two DuckDB threads, no temporary-disk spill, a 100-row preview, and a three-second interrupt budget. These controls prevent an approved request from returning a partial result after a timeout; they are not a guarantee that arbitrary analytical SQL is semantically correct, that the model always chooses the intended null/rank behavior, or that a shared deployment has sufficient capacity. The reviewer must inspect the proposed SQL, assumptions, filters, null handling, grouping grain, and window ordering before approval. A local Entra-authenticated Foundry proposal-to-approved-execution workflow is verified; a public deployment and availability/SLO evidence are not present.
